# 体裁路由

先按**读者要用这份报告做什么**选体裁，一次只读一个体裁文件。关键词只用于召回，不单独决定路由；排除信号优先于同名词（例如“项目报告”既可能是进度周报，也可能是复盘）。拿不准时在识别预设里列出最多两个候选，让用户选。

## 路由表

| 读者任务 | 常见叫法 | 体裁文件 | 排除 / 转去 |
| --- | --- | --- | --- |
| 按周期判断当前相对目标 / 计划的位置、偏差、风险和下一步 | 日报、周报、双周报、月报、季报、进度报告、项目状态、迭代报告、OKR 进展 | `status-report.md` | 解释已结束周期为何如此 → 复盘；完整指标解读 → 数据报告 |
| 对一段较长时期的个人或团队工作做总结与评价 | 年终总结、半年总结、述职、转正答辩、个人工作总结、晋升材料 | `work-summary.md` | 只报本周状态 → 状态报告 |
| 对照标准检查对象是否合格，给出结论与整改要求 | 审查报告、审计报告、质量审查、代码审查汇总、合规检查、上线评审、验收评审、巡检报告 | `review-audit.md` | 只是记录测试执行结果 → 测试报告 |
| 从已结束的周期或事件中提炼可复用的学习 | 复盘、回顾、经验教训、项目总结会、GRAI、KISS | `retrospective.md` | 仍在止损的事故 → 事故报告 |
| 说明一次故障 / 事故的影响、时间线、原因、恢复和改进 | 故障报告、事故报告、Postmortem、RCA、线上问题报告、8D 报告 | `incident-report.md` | 只为团队学习、不含处置 → 复盘 |
| 评审或说明一个技术设计、架构或实现方案 | 技术方案、技术报告、RFC、架构设计、设计评审、技术分享报告 | `technical-report.md` | 还在比较选项、靠实验判断 → 技术验证 |
| 用实验回答“某技术 / 方案是否可行、哪个更好” | 技术验证、POC、原型验证、选型报告、性能压测、基准测试、A/B 技术实验 | `tech-validation.md` | 方案已定只讲设计 → 技术报告 |
| 报告测试执行结果与质量结论 | 测试报告、验收报告、质量报告、上线报告、回归报告、UAT 报告 | `test-report.md` | 按标准做合格性审查并给整改 → 审查报告 |
| 解读已定义的指标、趋势、分布、漏斗 | 数据报告、经营分析、运营日报 / 周报（以指标为主）、销售数据分析、指标复盘 | `data-report.md` | 需要重新设计样本回答问题 → 调研报告 |
| 回答一个明确的研究问题 | 调研报告、用户研究、竞品分析、市场调研、访谈 / 问卷报告 | `research-report.md` | 只解读既定指标 → 数据报告 |
| 比较商业选项的价值、成本、风险 | 商业分析、可行性分析、投资分析、自建 vs 采购、市场进入分析 | `business-analysis.md` | 要具名决策者批准 → 提案 |
| 请求具名决策者批准方向、预算、资源 | 提案、立项申请、资源申请、预算申请、方案汇报（求批） | `proposal.md` | 方向已定只讲怎么执行 → 执行计划 |
| 方向已定，组织交付、依赖、里程碑、验收 | 项目计划、实施方案、执行方案、上线计划、迁移方案、活动方案 | `execution-plan.md` | 仍在求批 → 提案 |
| 让具名读者快速知悉或做会前准备 | 简报、备忘录、决策摘要、会前材料、情况通报、专报 | `memo-brief.md` | 完整论证求批 → 提案 |
| 记录已发生会议的决定、未决和行动 | 会议纪要、会议记录、评审会纪要、周会纪要 | `meeting-minutes.md` | 逐字稿只作素材 |

## 组合与嵌套

- 一份报告只有一个**主体裁**，决定结构骨架和首屏内容；其他体裁的内容可以作为章节出现。例如事故报告的最后一章可以是复盘层的“改进实验”，月报的一章可以是数据报告式的指标解读。
- 同一素材要交给不同读者时，按读者分别路由：给上级的是状态报告，给技术团队的是复盘。
- 体裁决定“写什么”，行业文件决定“用什么口吻和指标”，两者叠加使用：制造业 + 月报、互联网 + 审查报告。

## 所有体裁共通的失败条件

- 首屏看不到结论、状态或 ask；
- 事实、推断、建议、未知混写；
- 编造数字、完成率、原因、owner、日期或批准状态；
- 风险埋在正文里，或没有影响和所需支持；
- 行动没有负责人、时间和完成标准；
- 为了“看起来完整”套模板、凑章节、凑图表。
