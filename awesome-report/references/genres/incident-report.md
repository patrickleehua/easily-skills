# 事故报告：故障 / 事故 / Postmortem / RCA / 8D

## 定位

说明一次已发生故障或事故的**影响、时间线、原因、处置、恢复与改进**，让管理者判断严重程度、让团队防止再发。软件故障、生产质量事故、安全事件、客户投诉升级都适用。

**排除**：只为团队学习、不含处置过程 → `retrospective.md`；事故仍在进行、需要排查指导 → `technical-report.md` 的诊断模式。

## 硬约束

| 项 | 规则 |
| --- | --- |
| 写作 | 客观、精确到分钟、无责备；用“系统 / 流程 / 条件”做主语，不写“某某粗心” |
| 逻辑 | 摘要（影响 + 根因一句话 + 当前状态）→ 影响范围 → 时间线 → 根因与促成因素 → 处置与恢复 → 改进措施 → 附录 |
| 事实 | 时间线每条有来源（告警、日志、聊天记录）；止损、根因、永久修复分开写；根因证据不足时写“当前最可能原因 + 待验证项” |
| 失败 | 时间线缺关键节点（发现 / 定级 / 止损 / 恢复）、影响无量化、根因停在“人为失误”、改进措施无负责人和验证、未说明是否会再发 |

## 结构骨架

1. **摘要**：发生了什么、影响多大、持续多久、根因一句话、当前是否已恢复、是否可能再发。
2. **影响**：受影响用户 / 订单 / 批次 / 金额 / 时长，影响的业务功能，客户是否感知。
3. **时间线**：发生 → 发现 → 定级 → 止损 → 恢复 → 确认，标出发现延迟和恢复耗时。
4. **根因分析**：直接原因 → 根本原因（5 Why）→ 促成因素；多因素用鱼骨图。
5. **处置复盘**：哪些做得好（保持），哪些拖慢了恢复。
6. **改进措施**：短期（已完成）/ 长期（监控、告警、预案、流程、架构），每项有负责人、期限、验证方式。

制造业质量事故按 8D：D1 团队 → D2 问题描述 → D3 临时措施 → D4 根因 → D5 永久对策 → D6 验证 → D7 预防再发（横向展开到同类产线 / 工序）→ D8 总结。

## HTML 组件配方

| 位置 | 组件 |
| --- | --- |
| 首屏 | `summary` + `kpis`（影响用户 / 持续时长 / 发现耗时 / 恢复耗时）+ `highlights` |
| 影响 | `table` 或 `kpis` |
| 时间线 | `timeline`（关键节点用 status 标注；异常节点 `risk`） |
| 根因 | `fishbone` + `evidence`（事实 / 推断 / 未知） |
| 处置复盘 | `grid`（做得好 / 需改进） |
| 改进 | `actions`（短期已完成标 done）；8D 用 `table`（问题 / 根因 / 临时措施 / 永久对策 / 责任人 / 状态） |
