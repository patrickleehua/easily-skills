# 审查报告：审查 / 审计 / 质量审查 / 合规检查 / 上线评审 / 验收评审

## 定位

对照明确标准检查一个对象（系统、交付物、流程、项目、账目、现场）是否合格，给出**结论、依据、问题分级和整改要求**。读者要据此做“通过 / 不通过 / 有条件通过”的决定。

**排除**：只记录测试执行结果不做合格判断 → `test-report.md`；从事件中提炼经验 → `retrospective.md`。

## 硬约束

| 项 | 规则 |
| --- | --- |
| 写作 | 中立、精确、可复核；结论措辞与证据强度一致，不写“基本合格”“总体良好” |
| 逻辑 | 审查结论与决策建议 → 审查范围、标准与证据口径 → 发现（按严重程度分级）→ 阻断项与整改要求 → 复验条件 → 附录（原始材料索引） |
| 事实 | “已核查事实”“基于事实的判断”“建议决策”分开写；每条发现能回查到证据位置；缺证据的项标“待确认”，不计入通过 |
| 分层 | 测试通过、代码已合入、评审写 pass、Git 有提交分别只证明对应层面，不自动等于“已交付”“可上线”“已签核” |
| 失败 | 结论与证据不符、问题不分级、整改无负责人和验收标准、把待确认算作通过、审查范围不清导致结论外推 |

## 结构骨架

1. **审查结论与决策**：通过 / 不通过 / 有条件通过；一句话理由；重新评审条件。
2. **范围、标准与证据口径**：审查对象与版本、依据的标准或清单、证据来源及其边界。
3. **审查发现**：编号、描述、等级（阻断 / 一般 / 建议）、证据位置、状态。
4. **阻断项与整改要求**：每项写整改动作、负责人、期限、复验方式。
5. **检查清单**：逐项状态，缺证据的单列。
6. **后续验收与附录**：复验门、原始材料索引。

## 状态隐喻处理

“全绿”“测绿”“跑通”必须展开成：哪一层宣称成功、证明了什么没证明什么、读者该看什么证据（见 `writing-core.md` 第四节）。审查报告尤其要区分“测试通过”与“功能可用”。

## HTML 组件配方

| 位置 | 组件 |
| --- | --- |
| 首屏 | `summary`（结论 + 重新评审条件）+ `highlights`（结论 / 已达标 / 重新评审条件）+ `kpis`（检查项 / 通过 / 阻断 / 待确认） |
| 结论与决策 | `decisions`（带理由与生效条件） |
| 证据口径 | `evidence`（事实 / 推断 / 未知分开） |
| 发现 | `table`（`level` + `status` 列，阻断行 `_tone: risk`）+ `donut` / `stacked`（结果构成） |
| 清单 | `checklist` |
| 整改 | `actions`（P0 = 阻断项，含验收标准） |
| 严重度分布 | 必要时 `risk-matrix` |

示例：`assets/examples/audit-review.json`。
