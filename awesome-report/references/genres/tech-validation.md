# 技术验证：POC / 选型 / 性能压测 / 基准测试 / 技术实验

## 定位

用实验回答一个具体问题：“某技术 / 方案在我们的条件下是否可行”“几个选项哪个更好”。读者要据此做采用、放弃或继续验证的决定。

**排除**：方案已定只讲设计 → `technical-report.md`；上线前质量合格判定 → `review-audit.md` / `test-report.md`。

## 硬约束

| 项 | 规则 |
| --- | --- |
| 写作 | 结论先行、带条件；结论强度不超过实验覆盖范围 |
| 逻辑 | 验证问题 → 判据（事先确定）→ 环境与方法 → 候选方案 → 结果 → 结论与适用边界 → 遗留风险与下一轮验证 |
| 判据 | 判据在实验前确定并写明阈值；不能因结果调整判据，调整了要说明原因 |
| 可比性 | 各方案同硬件、同数据、同负载、同版本；不同口径的数据不排名 |
| 边界 | 明确写“本轮没测什么”（规模、并发、多租户、故障场景……），不外推 |
| 失败 | 判据后定、环境不一致、只报最好的一次、样本量 / 轮次不写、把“能跑”写成“可用于生产”、隐藏失败数据 |

## 结构骨架

1. **结论**：推荐哪个 / 是否可行，满足几项判据，前提条件是什么。
2. **验证目标与判据**：一个问题，3–6 条判据（指标 + 阈值 + 测量方式）。
3. **环境与方法**：硬件、数据规模、版本、工具、轮次、负载模型。
4. **方案对比**：各方案在每条判据上的结果。
5. **详细结果**：曲线、分布、异常点及解释。
6. **结论边界与遗留风险**：没测到的场景、已知风险、下一轮验证计划。

## HTML 组件配方

| 位置 | 组件 |
| --- | --- |
| 首屏 | `summary` + `highlights`（推荐 / 未验证 / 决策点）+ `kpis`（关键指标，`target` 写判据） |
| 判据 | `table`（判据 / 阈值 / 测量方式）或 `checklist`（逐条达标情况） |
| 方案对比 | `comparison`（单元格按是否达标上色，`verdict` 写结论） |
| 结果 | `line`（指标随负载变化）、分组 `column` / `bar`（多方案同指标）、`heatmap`（参数组合） |
| 过程 | `steps` |
| 结论与边界 | `callout`（warn：结论适用边界）+ `decisions` + `risks` |

示例：`assets/examples/tech-validation.json`。
