# 技术报告：技术方案 / RFC / 架构设计 / 技术说明

## 定位

让评审者能批准并实现一个技术设计，或让读者系统理解一项技术实现。必须且只能选一种主模式：

| 主模式 | 读者任务 | 推进顺序 |
| --- | --- | --- |
| 设计方案（RFC） | 评审并批准未来的技术状态 | 问题证据 → 目标 / 非目标 → 约束 → 真实备选与取舍 → 设计 → 失败 / 安全 / 兼容 / 迁移 → 上线与回滚 → 可观测与验收 → 未决问题 |
| 技术说明 / 接口说明 | 调用者或维护者不猜就能用 | 版本 / 环境 / 权限 → 输入输出与行为 → 错误与恢复 → 限流 / 重试 / 兼容 / 弃用 |
| 故障诊断 | 在未知中安全地缩小范围、止损、恢复 | 影响与预期 / 实际 → 证据链 → 可证伪假设 → 低副作用高信息量的检查 → 止损与恢复验证 → 升级 |

**排除**：靠实验比较方案 → `tech-validation.md`；产品行为与验收 → PRD（不在本技能范围）；事故结束后的完整报告 → `incident-report.md`。

## 硬约束

| 项 | 规则 |
| --- | --- |
| 写作 | 精确、可证伪、术语与版本稳定；“必须 / 应当”只用于明确的规范语义 |
| 事实 | 标对象、环境、版本、时间、范围和证据位置；事实、推断、决定、未知分开；代码与命令示例须实际验证并标环境 |
| 设计 | 每个关键决定写：为什么、被否方案及其后果；不隐藏低置信度或版本偏差 |
| 图 | 架构 / 状态 / 时序图必须附文字说明，不能是唯一证据或唯一操作说明 |
| 失败 | 多种模式混写、设计无取舍无验收、改状态的操作没有授权 / 停止条件 / 回滚、未知故障直接定根因 |

## HTML 组件配方

| 位置 | 组件 |
| --- | --- |
| 首屏 | `summary`（推荐方案一句话 + 需要评审的决定）+ `highlights` |
| 背景与目标 | `markdown` + `grid`（目标 / 非目标） |
| 约束 | `checklist`（约束与不变量） |
| 方案取舍 | `comparison`（带 `verdict`）+ `decisions`（关键决定与被否方案） |
| 设计细节 | `markdown`（接口、数据、状态说明）+ `table`；架构图 / 时序图用 archify 生成后以 `image` 嵌入 |
| 上线与回滚 | `steps` + `gantt` |
| 风险与未决 | `risks` + `decisions`（status: pending） |
| 术语 | `glossary` |
