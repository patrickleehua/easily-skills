# 写作核心规范

所有体裁、所有行业、所有输出形式共用这一层。体裁文件规定“写什么、按什么顺序”，行业文件规定“用什么口吻和指标”，本文件规定“怎样写才可信、好读”。吸收自 feishu-doc-style-1E 的写作与证据规则。

## 一、证据契约（先于写作）

动笔前建一份来源台账，每条记录：来源（文件、链接、会话、提交、日志、数据查询）、证明了什么、范围 / 版本 / 日期、已知缺口，以及性质——**已核查事实 / 推断 / 建议 / 未知**。HTML 里可直接用 `evidence` 组件呈现。

硬约束：

- 不编造事实、来源、引语、数量、分数、路径、ID、日期、接口参数、界面文案、原因、结果和未来承诺。缺什么写 `待确认`，或写“现有材料不能证明”。
- 不把“可能 / 通常 / 建议 / 计划 / 待确认”加强成确定语气。
- 不改主语、宾语、因果方向、比较基线和范围。
- 不删限制条件、例外、风险、默认值和失败条件。
- 代码、链接、路径、命令、字段名、标识符、引文一字不改。
- 不为了“看起来改过”去改本来就具体、有用的句子。

## 二、结构：总分总

信息顺序固定：**概要与结论、总数、易扫读内容在前；长表、详细日志、来源路径、附件在后。** 不单独开“如何阅读本文”一章，阅读说明并入范围或方法。

报告类默认骨架（按体裁增删，不机械扩章）：

1. 概要与结论
2. 条件与方法（范围、口径、证据边界）
3. 主体分析
4. 图表与证据
5. 结论与下一步
6. 来源与附件

编号用 `一、` / `1.1` / `1.1.1`（HTML 设 `"numbering": "cn"` 自动加），同级连续、子级必有父级。只有两三句话的节并入上一节，不造薄标题。

**每章先写事实导语**：第一个表格或列表之前至少两句话——这一章回答什么问题 + 一个可核查的事实。导语不是目录预告。HTML 里写在 `sections[].lead`。

## 三、正向写法

- 开头直接给最重要的问题、结果、决定或矛盾。
- 先给读者一个可用的整体认识，再讲边界情况和附件。
- 一段只讲一个要点；主语和动词具体。
- 论断连到例子、数据或明确标注的经验。
- 过渡词表达真实的时间、因果、转折、条件或后果，不用来掩盖缺失的因果。
- 标题和列表只在改善导航时使用；列表项要平行、回答同一个问题。
- 结论回答开头的问题，并写清还有什么没解决。
- 保留作者真实的确定程度和判断。

**概要里说人话**：不把晦涩术语、内部代号、裸代码当主要措辞，改成“发生了什么、查了什么、读者该看什么”的通俗技术说明。必须保留的术语首次出现时解释（可用 `glossary` 组件），之后保持一致。精确的命令、路径、ID 放在细节、表格或附件里。

不用违禁词表代替理解段落；机械换同义词仍然是错的语气。

## 四、状态隐喻必须展开

“全绿 / 测绿 / 假绿 / 跑通了 / 假死”这类说法把验证结果压缩成比喻，读者看不到三件事。改写时展开：

1. **哪一层宣称成功**：任务自检、单元测试、门禁脚本、评测……
2. **这个成功实际证明了什么、没证明什么**：覆盖范围、未验证的部分。
3. **读者应该看什么可观察证据**。

示例方向（不是黑名单）：

- `全绿`：写清哪些检查通过、凭什么证据、覆盖多大、还有什么没验证。若只是表面通过，说出机制——测试套件没编进去、断言匹配了桩、空集合断言、门禁没接到主路径。
- `假死`：写清多长时间内没有新日志、状态变化、心跳或退出码；没有终止证据不说“已终止”。
- `跑通了`：写清哪条路径、什么输入、什么输出、经过什么验证。
- 缺主语宾语的口号式短句：补成完整分句——谁、对什么、做了什么、否则会怎样。

同理：“测试通过”“代码已合入”“评审写 pass”分别只证明对应层面，不自动等于“已交付”“可上线”“已签核”。

## 五、结构性问题自查

找模式，不找孤立的词：

- 开头或结尾只复述标题，没有新信息；
- 权威或背景没有来源；
- 抽象夸奖没有对象、动作、结果；
- 一个精确术语被几个近义词轮换；
- 列表项不平行，或回答的不是同一个问题；
- 过渡词掩盖了缺失的因果或时间关系；
- 段落宣称“很复杂”却不说具体有哪几部分；
- 局部观察被放大成普遍结论；
- 润色后丢了条件、例外或不确定性标记。

每个问题定位它的信息作用，给最小修复；改完重读上下文。不做全局查找替换式改写。

## 六、语义色

颜色只用来提高状态、类别或重点的可扫读性，不作装饰：

- 一种含义一种颜色，全报告一致（组件的 `tone` / `status` 已内置这一规则）；
- 颜色只做强化，永远配文字标签（组件的徽标都带文字）；
- 表头保持中性，着色单元格只表达状态或类别；
- 提示框、高亮默认浅底，深色只给硬性警告；彩色字只强调短语，不整段上色；
- 不做整页装饰色、不叠加无解释的渐变；
- 红黄绿等健康色必须有判据（`rag` 组件强制要求 `criteria`）。

## 七、视觉选择：让图回答问题

先想这张图回答什么问题，再选形式：

| 要回答的问题 | 选用 |
| --- | --- |
| 流程 / 分支 / 审批链 | `steps`；复杂流程、泳道、架构用 archify 或飞书画板 |
| 生命周期 / 阶段推进 | `timeline`、`steps` |
| 计划 vs 实际排期 | `gantt` |
| 类别比较 | 排序后的 `bar` 或 `table` |
| 时间趋势 | `line`（写明时间范围和单位） |
| 构成 | `stacked`；只有少数几部分时用 `donut` |
| 目标达成 | `scorecard`、`gauge` |
| 贡献拆解 | `waterfall` |
| 两维交叉强度 | `heatmap` |
| 阶段转化 | `funnel` |
| 方案取舍 | `comparison` |
| 优先级 / 风险定位 | `quadrant`、`risk-matrix` |
| 根因 | `fishbone` |

每张图写明来源、单位、时间范围、分母或样本量，并在旁边用一句话写“读者该注意什么”。复杂视觉要有文字等价信息，任何图都不能是唯一证据。

## 八、交付前自检

**信息**：读者、目的、范围、版本、来源权威明确；每个论断有支撑或标为推断 / 建议 / 未知；数字、姓名、引语、条件、归属和不确定性完整；术语、命令、标识符、路径、链接准确。

**结构与文风**：总分总；编号连续有父级；每章有事实导语；段落一个要点且有新增信息；概要说人话、术语已解释；无违禁词式替换或强行口语化；状态隐喻已展开；没有夸大的结论和空泛的升华结尾。

**视觉**：图回答了预期问题；带来源、标签、单位、时间范围和文字等价；颜色表义一致且不单独承载状态。
