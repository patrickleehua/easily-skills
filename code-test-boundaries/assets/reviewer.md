## 实现与验证必要性审查

先看当前契约、可达风险和有效证据是否充分，再审新增复杂度。生产／测试行数比、用例数或“还能测更多”不能单独成为返工理由。新增抽象、配置、依赖和兼容分支须有当前责任；不能只为未来可能复用扩建。

新增永久测试应保护具体契约、识别具体错误，并有相对现有回归的持续价值。复述内部步骤、重复等价断言、耦合私有细节或无作用 mock，可有依据地建议合并；不同边界、状态、真实接缝和错误机制不能机械合并。

要求补测时，指出哪条必要验收或相关风险缺有效证据、会漏掉什么失败。已有检查能支持结论时不强制新建文件；必要集成、真实 UI／协议／宿主验证及指定专业方法不能被单测或模拟替代。额外增强列建议，沿用原严重度、复审范围、轮次及人工出口，不增加“全部优化才可通过”的条件。

环境缺失本身不是代码缺陷。分别审实现正确性、运行证据和专业完成度；充分、独立、可复核的契约、入口、调用链、边界与失败路径证据，可支持限定范围的正向源码结论。核对未知前提、适用版本和未覆盖风险，不能只凭“看着合理”认定正确，也不替实施者修环境或修改代码。

当前审查所需证据充分、且不缺必要验收时，可按已核范围裁决，运行未验面单列。明确必要的真实验收缺失或关键证据不足时，依原合同列具体缺口；原合同要求必要 e2e 非通过则阻塞的规则继续生效。非必需平台或增强不自动成为新阻塞。

在原输出中说明有依据支持的行为、运行通过／失败／未验范围及恢复所需条件。源码判断、专业完成、评审裁决与流程推进不能换算成实测通过；环境归因不改写原始结果。保持原只读边界和输出语义，证据充分即收口，不要求额外评估报告。
