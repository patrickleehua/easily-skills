# 接入专家与研发 SOP

目的是让真正作出实现、测试和评审决定的角色使用规则，保留宿主原有控制。不要按专家名字猜职责，也不要给全体角色复制同一份长文。

## 接入前先读目标

查看目标仓库的 `AGENTS.md`、专家定义、SOP、安装／生成入口及相邻惯例，确认：谁写生产代码，谁写测试，谁只读评审；哪些检查或方法强制执行；专业完成、技术通过、验收裁决分别如何表达；复审如何退出。

按实际职责选择材料：

| 本次承担的职责 | 需要做什么 | 接入材料 |
|---|---|---|
| 需求与验收负责人 | 说明业务范围、可观察结果、兼容要求和必须完成的验收；依原流程处理验收变更 | 通常不加载角色片段；提供权威判据即可 |
| 代码实施者，包括前后端、脚本和配置开发 | 在正确责任边界修根因，控制新增分支、抽象和依赖，完成必要自验证 | [实施片段](../assets/implementation.md) |
| 测试设计与执行者 | 找出证据缺口，选择有区分力的判据与验证层次，决定哪些新增测试值得长期保留 | [测试片段](../assets/tester.md) |
| 独立评审者 | 检查实现与证据是否满足必要契约，区分交付缺口和额外优化建议 | [评审片段](../assets/reviewer.md) |
| 安全、性能、运维、数据等专项角色 | 当前任务确有对应风险时，用专项方法处理；承担实现、测试或评审职责时选相应片段 | 按实际工作选择，不因职位名自动加载 |
| 文档、协调或纯咨询角色 | 完成原有职责；不因此新增代码、测试或验收裁决权限 | 通常不加载角色片段 |
| 有专门修复方法的维护角色 | 保留明确要求的缺陷复现、先红后绿、全量回归等方法 | 逐条检查冲突后再选相关片段 |

每个片段可单独使用，不要求专家同时读取 `SKILL.md` 或其他片段。适配时把术语对应到原合同，合并已有同义规则；保留文件头、权限和返回格式，不平行堆叠多个版本。若与明确必做项冲突，缩小本片段适用范围。

同一个人或代理可以承担多个职责，但不得据此取消原流程要求的独立评审。只给它加载当前工作需要的片段，不新增代理数量要求。

只把判断原则放进角色定义或 SOP 的判断分支。安装、任务分配、日志、验证记录、权限和状态迁移留给已有实现。修改角色定义后检查其配置生成／加载链路；源文件更新不证明现有实例已加载。

## 新 SOP 的最小接入方式

已有 SOP：补到原有“实施取舍、验证、环境缺口、交付”节点。没有这些标题也不必新增四套流程，只须让相关决定有明确归属。

新 SOP：先明确输入、职责与授权、现行验收和输出，再嵌入本技能的判断。不强制给小任务建立风险台账或新报告。下面可直接用作任务提示：

```text
使用 $code-test-boundaries，为当前仓库接入实现和测试投入规范。
先读仓库约定、目标专家／SOP 及安装生成链路，按实际职责选择实施、测试、评审片段。
保留必做检查、专业方法、写范围、返回状态、复审轮次和人工出口，合并已有同义规则。
只在必要角色和原有节点补判断，普通任务不新增必填报告。
交付可审查的改动与适用边界，核对环境不足、停止条件和恢复入口；只在授权范围内修改。
```

提示词中的“接入”必须结合用户实际授权解释；仅要求建议时交付适配文本，不自动写入角色定义或安装。

## 工作完成、验证结果与交付决定

接入前明确三类结论由谁记录、由谁决定，不要求新增机器状态或输出字段：

| 结论 | 含义 | 处理方式 |
|---|---|---|
| 当前职责是否完成 | 角色要求的实现、检查、分析或交接是否完成；完整失败分析也可能是已完成的工作 | 执行者按既有输出说明，评审者核对范围 |
| 验证实际结果 | 哪些检查通过、失败或未执行，以及所对应的版本、输入和环境 | 保留原始结果与证据，不因环境归因重写事实 |
| 能否验收或继续推进 | 是否满足当前必需条件，或是否有权接收明确的剩余风险 | 由原流程指定的验收者、评审者或负责人决定 |

例如：测试者已完成授权范围内的检查与障碍定位，真实联调仍未执行。可以如实交接已完成的工作和复跑条件；必需联调的验收缺口继续保留，能否推进沿原流程决定。评审停止条件、复审次数及人工处理方式也沿用目标流程。

## 技术栈与程序化边界

本技能是 Markdown＋YAML，没有运行脚本、服务、包依赖或新状态机。判断依赖契约和上下文，硬编码“允许多少行／几个用例”无法代替判断。

以后有确定、重复、可测的动作才增加代码。例如，记录版本与命令结果、校验报告格式、检查已登记证据是否对应当前输入。优先接现有工具，按目标项目的运行环境与维护能力选技术栈；简单重复动作用独立脚本，复杂共享能力用工程模块，必要平台差异由适配层处理。不要求统一改写稳定工具，也无需为了使用本技能安装语言运行时。

程序可以校验格式、权限、超时、明确状态迁移及已登记强制检查；“这些证据在业务上是否充分”仍需专业判断或人工裁决，不能用模型自报通过充当硬门禁。引入脚本后才声明运行时、锁定依赖、定义输入输出与错误，并验证相应平台和宿主。

## 如何确认复用有效

先静态检查职责、强制项和原输出语义，再用代表性真实任务试用：普通重构、少行高风险修复、跨层交互、环境缺失。观察必要缺陷是否仍能被识别、无价值新增是否减少、未验是否如实表达、交接能否恢复。

以漏检／误阻塞、证据有效性、重复维护负担及无理由重试为依据迭代。少写了多少行测试不能单独证明有效；结构校验和案例推演也不能代替真实宿主试用。
