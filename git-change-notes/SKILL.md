# Git 变更说明规范

为同一批真实变更建立统一口径，再按 commit、合并与发布场景调整粒度。默认使用中文正文、英文 Conventional Commit 类型与 release 分类标题；遵循用户指定语言和仓库已有规范。

## 1. 确定场景和实际流程

- 读取适用的 `AGENTS.md`、最近同类说明，以及与当前场景有关的 commitlint、release、changelog 配置；复用已有生成工具和版本策略。
- 将本 skill 作为现有 mg、commit、tag 等工作流中的“说明生成与审查”步骤；保留工作流原有执行方式、分支策略和权限边界。
- 区分操作：`draft` 生成文案，`review` 检查已有文案，`apply` 将已生成的规范说明用于当前已获授权的操作。未指定时根据用户任务推断。
- 先检查 `mg` 的项目文档、Git alias、脚本或已知技能定义，确认它是 merge、merge-and-tag 还是其他流程。不要仅凭缩写执行命令。无法确定时仍可整理已知变更并标明场景假设；仅在执行依赖该定义时询问。
- 对复合流程依次生成相应产物，例如 mg → merge/PR 说明 → squash commit → tag annotation → release notes；不把一种文案原样复制到全部场景。

| 场景 | 证据范围 | 输出粒度 |
| --- | --- | --- |
| commit / squash | 本次实际提交的 patch | 一个主题的类型、模块、行为变化；按需补原因与破坏性 footer |
| mg / merge / PR / MR | 源分支相对目标的变化，或最终合并结果 | 最终目的、主要变化、兼容性、真实验证、关联事项 |
| tag annotation | 明确目标 commit 和对应版本范围 | 版本身份、主要变化、兼容性提醒；保持便于命令行阅读 |
| release / changelog | 同组件基线到目标的最终净变化 | 破坏性变更置顶，分类汇总全部实质变化，保留来源链接 |

读取 [证据与范围规则](references/evidence.md) 选择正确的 diff。读取 [场景模板](references/templates.md) 中对应部分，不必加载全部模板。仅在需要解释或调整参考写法时读取 [参考风格](references/reference-style.md)。

## 2. 建立真实变更记录

在内部为每个独立变化整理以下字段，不要求向用户展示中间表：

`category | scope | before → after | reason | consumer impact | migration | source commit/PR | verification`

- 以实际 diff、相关代码/契约、最终文件状态为事实依据；用 commit message 和 PR 描述辅助定位，不把它们当成实现证明。
- 固定仓库、场景、基线和目标；在执行前复核对应 patch/ref 没有变化。
- 对 commit 只描述本次纳入的 patch；区分 staged、unstaged 和 untracked。没有暂存时不要自行 `git add`。
- 对合并说明反映最终变化，单独说明实际冲突解决造成的行为变化；不要把同一变化按每个中间提交重复描述。
- 对 release 使用同组件、同发布线的基线，纳入影响该组件的共享变更；不能用其他包的最新 tag 代替。
- 合并相同最终效果，移除已完全回滚且未留下影响的变化；为每条保留真实来源，确保实质变化均被覆盖。
- 无法读取仓库时使用用户提供的材料生成有限草稿，明确缺失依据；不编造版本、日期、hash、PR、链接、性能数据或验证结果。

## 3. 写出具体、可追溯的说明

默认采用：`scope: 动作 + 可观察的行为变化 + 必要的条件/影响（来源）`。

- 使用实际模块或能力边界作 scope，例如 `cli`、`browser`、`javascript`；优先使用仓库约定的 scope。
- 写明变化后的行为。在修复不易理解时补充触发条件和之前的错误行为；只有证据支持时才解释设计原因。
- 将“优化逻辑”“完善功能”“修复一些问题”“更新若干文件”等泛化表述改为具体变化。
- 不把目录清单、工时、代码行数、完整 diff 或逐条提交日志当成变更说明。
- 小提交只写必要内容；大型版本保留全部实质变化，可按模块继续组织，不强行截断为少数亮点。
- 对外说明优先写使用者可感知的效果；架构、文档、测试和 CI 的变化放入对应分类，避免包装成新功能。
- 仅引用已核实的 commit/PR/issue/文档链接。提交尚未生成时省略自身 hash；无远端 URL 时保留已知短 hash，不拼接假地址。

| 类型 | Release 分类 | 判定 |
| --- | --- | --- |
| `feat` | Features | 新增可用能力 |
| `fix` | Bug Fixes | 修正已有行为 |
| `perf` | Performance Improvements | 有依据的性能相关变化；数值需测量来源 |
| `refactor` | Code Refactoring | 行为保持不变的内部结构调整 |
| `docs` | Documentation | 文档变化 |
| `test` | Tests | 测试和 fixture 变化，不代表测试已运行 |
| `ci` | Continuous Integration | CI 工作流与门禁 |
| `build` | Build System | 构建、依赖、打包变化；有用户影响时按实际效果分类 |
| `chore` | Miscellaneous | 不属于其他类型的维护变化 |

按最终实际效果判断，不照搬可能不准确的历史前缀。同一个问题同时修改实现和回归测试时通常归入 `fix`，不重复生成独立 Tests 条目；独立测试体系变化才单列。

## 4. 优先处理破坏性变更

- 检查公开 API、CLI 参数、schema、返回类型、序列化、默认行为、最低运行环境和已持久化数据的兼容性；内部变化不自动视为 breaking。
- 将消费者需要调整的变化放在 release 的 `⚠ BREAKING CHANGES` 首节；写清旧行为、新行为、受影响对象和实际可执行的迁移步骤。
- 若当前 patch 本身有破坏性变化，使用 `type(scope)!: summary` 和 `BREAKING CHANGE: ...` footer，除非仓库明文规定其他等价格式。
- 将同一变化的 breaking 条目作为主说明；若还列入普通分类，使用简短交叉引用，避免重复长段落。
- 无迁移方案证据时说明已知影响和待确认步骤，不发明转换工具、兼容模式、备份格式或命令。
- 不根据参考项目的版本数字推断当前项目的版本；采用当前仓库的组件版本和发布策略。只在用户请求时提出版本建议。

## 5. 按场景交付和应用

- `draft`：交付可直接复制的正文；将缺失依据或待确认项放在文案外。证据不足以支持正式发布的内容标记为草稿。
- `review`：列出影响正确性的具体问题及证据，再提供修订全文；没有问题时说明通过，不为风格偏好强加修改。
- `apply`：在当前操作已获授权时，先完成文案和必要校验，再通过项目现有工具写入；不重复询问已获授权的操作。
- 对尚未执行的复合流程标明预计结果与当前来源。新 merge/squash commit 产生后，重新核对最终 diff，并刷新后续 tag/release 的目标和来源；不要把计划中的 hash 当成已存在的对象。
- 不从“写说明/创建规范”推导出 commit、merge、push、创建或移动 tag、发布 release 的授权。不要安装 hooks、修改 Git alias 或替换项目配置，除非任务明确要求。
- 使用支持多行文本的结构化参数或 UTF-8 临时文件；CLI 优先 `git commit -F`、`git tag -a -F`、`gh ... --body-file`。不要将正文拼入 shell、压成字面量 `\\n` 或交给命令替换。
- 把 Git tag annotation 和托管平台 release body 作为两种独立产物；创建 tag 不等于发布了 release。
- 写入后读取实际 commit/tag/release 进行核对，再报告完成的操作、目标版本/ref 与真实验证结果；失败时报告准确状态。

## 6. 交付前自检

1. 核实仓库、场景、实际 patch 或基线/目标，以及版本所属组件。
2. 确保所有事实、来源、兼容性结论和验证声明有证据，且与最终状态一致。
3. 将 breaking 置顶并补迁移影响；删除空分类、占位符和无意义套话。
4. 确保范围内的实质变化完整且去重，用户影响没有埋在测试或重构分类中。
5. 区分“有测试代码”“本地运行通过”“CI 通过”；引用验证记录时匹配 patch/commit，未运行写明未运行。
6. 仅运行项目要求和本次操作必要的检查；生成说明本身不要求新增测试或运行无关全量测试。
7. 确保文案长度、语言、标题和链接适合当前场景及仓库规范，操作没有超出用户请求。
