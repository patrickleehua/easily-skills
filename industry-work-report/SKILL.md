# 行业化报告生成器

把零散的工作材料整理成“符合体裁规范、贴合行业口吻、证据可追溯”的报告，让读者 30 秒内看懂结论、风险和需要他做的事。

一份报告由三层叠加决定：

| 层 | 决定什么 | 在哪 |
| --- | --- | --- |
| **体裁** | 写什么、按什么顺序、首屏放什么、用哪些组件 | `references/genres/`（15 类，先读 `_router.md`） |
| **行业** | 用什么口吻、看哪些指标、常用模板 | `references/industries/`（14 个） |
| **写作核心** | 证据契约、总分总、说人话、状态隐喻展开、语义色 | `references/writing-core.md`（所有报告共用） |

## 核心原则

1. **不编造**：素材里没有的事实、数据、原因、负责人、日期一律不写；缺什么写“待补充 / 待确认”。
2. **结论先行**：首屏给结论、状态或需要的决定，细节往后放（总分总）。
3. **事实分层**：已核查事实、推断、建议、未知分开写；“测试通过”“已合入”“评审 pass”只证明各自那一层。
4. **风险不藏**：写清“卡点 + 影响 + 需要谁在何时做什么”；没有证据时写“待确认”，不写“无风险”。
5. **有依据才量化**：不为版式编数字，不把条目数量当完成率，不从“差不多”猜百分比。
6. **说人话、翻译成价值**：❌“完成接口联调” → ✅“支付接口联调完成，回归推进至 80%，为周四提测扫清阻塞”。概要里不堆黑话和裸代码，术语首次出现就解释。

## 工作流

### Step 0：大段素材先给识别预设

用户触发技能后直接贴大段素材（约 500 字以上、8 条以上工作项、多个日期或项目），且没说清体裁、行业、输出形式时，**先停在识别阶段**，给出可修改的预设：体裁、时间范围、行业、汇报对象、核心重点、风险、输出形式、视觉方案（HTML 时列出打算用的组件及数据来源）。用户确认或修改后再生成。用户已明确参数或说“直接生成”时跳过。细则见 `references/identification-preset.md`。

### Step 1：确定体裁

读 `references/genres/_router.md`，按**读者要用这份报告做什么**选一个主体裁，再只读对应的体裁文件。关键词只做召回：“报告”“总结”“方案”单独不决定体裁。拿不准时给两个候选让用户选。

### Step 2：确定行业

按以下优先级，只读命中的一个行业文件：

1. 用户明确说了 → 直接采用。
2. 按素材关键词推断：
   - 需求 / Bug / 联调 / 迭代 / 上线 / 灰度 / OKR → `internet-tech.md`
   - 客户拜访 / 线索 / 商机 / 成交 / 漏斗 / 渠道 → `sales-marketing.md`
   - 仓位 / 回撤 / 净值 / 尽调 / 标的 / 合规 → `finance.md`
   - 产线 / 良率 / 工单 / 设备 / 8D / BOM / 安全巡检 → `manufacturing.md`
   - 甲方 / 交付物 / 里程碑 / 投标 / 提案 → `consulting.md`
   - 处室 / 上级要求 / 贯彻落实 / 公文 → `gov-soe.md`
   - 实验 / 论文 / 课题 / 导师 / 招生 → `research-edu.md`
   - stakeholder / TL;DR / RAG / 英文汇报语境 → `foreign-enterprise.md`
   - 融资 / 获客 / MVP / 增长验证 / 小团队 → `startup.md`
   - 门诊 / 手术 / 床位 / 不良事件 / 临床 / 注册申报 → `healthcare.md`
   - 施工 / 形象进度 / 产值 / 签证 / 监理 / 节点工期 → `construction.md`
   - GMV / 客单价 / 转化率 / SKU / 门店 / 大促 / 直播 → `retail-ecommerce.md`
   - 招聘 / 报销 / 合同审核 / 工单 / 预算执行 / 采购 → `functional-support.md`
3. 推断不出：查本文件末尾“已知用户行业记忆”；仍无法判定用 `general.md`，生成后问一句行业，并把答案追加到末尾。

### Step 3：收集素材

依次取：本次对话给的材料 → 用户已有的报告（写月报先找周报，写周报先找日报）→ 技术类工作的 `git log`、README、任务清单。素材不足时一次性列出缺失项，或给带 `[待补充]` 的初稿，不反复追问。

### Step 4：提炼与证据台账

- 按 `writing-core.md` 建来源台账：每条事实记来源、证明了什么、边界、性质（事实 / 推断 / 建议 / 未知）。
- 归类去重；按体裁骨架分到各章；每章准备两句事实导语。
- 所有数字单独标出处、口径和时间点；冲突数据并列标 `[口径待核]`。

### Step 5：按输出形式生成

默认 Markdown。用户提到 HTML、可视化、网页汇报、展示模板时走 HTML；提到飞书、云文档、发到飞书时走飞书。

| 输出 | 做法 |
| --- | --- |
| **Markdown** | 按体裁骨架 + 行业模板写正文；不放图表和装饰。编号 `一、` / `1.1`，每章先写事实导语 |
| **HTML** | 读 `references/html-visualization.md` 与 `references/components.md`。从素材生成 JSON（或带组件代码块的 Markdown），首屏 = 结论 + 重点色块 + 有来源的指标；各章按体裁文件末尾的“组件配方”选组件，按行业文件末尾的“组件映射”补指标图；先 `--check` 再渲染，浏览器检查桌面与窄屏 |
| **飞书文档** | 先按 Markdown 路径成稿（编号、事实导语、语义色说明按 `writing-core.md`），给用户确认大纲；再交给 `lark-doc` skill **新建**文档。提供的现有文档链接默认只是素材，只有用户明确说“更新 / 改写这篇”才改原文；写入前取得明确授权，写入后回读核对。流程图、架构图用 `lark-whiteboard` 或 `archify` |
| **Word / PPT / Excel** | 交给对应 Office skill，内容结构不变 |

HTML 额外要求：**压缩正文**（每章导语 2 句、正文 ≤3 段）、**标出重点**（语气色一义一色、`==高亮==` 每段最多一处）、**按内容选图**（只画素材里有的数，每张图带 `source`，少于 3 个数据点改用指标卡或表格）。

### Step 6：自检后交付

- [ ] 首屏 3 行内能看到结论 / 状态 / 需要的决定
- [ ] 每个数字有出处和口径；没有编造数字、进度、趋势、原因、负责人
- [ ] 事实、推断、建议、未知分开；状态隐喻（全绿、跑通、假死）已展开成可核查的说法
- [ ] 风险有“描述 + 影响 + 需要的支持”，或明确写“待确认”
- [ ] 行动 / 计划有负责人、时间、完成标准，下期计划不超过 5 条
- [ ] 符合体裁文件的硬约束和失败条件；符合行业文件的口吻和指标
- [ ] 无模糊词和空话；概要说人话，术语已解释
- [ ] 对外场景已脱敏（客户全名、金额、内部数据、个人信息）
- [ ] HTML：`--check` 通过；桌面与约 390px 窄屏无溢出；打印预览可读；图表有来源且与正文一致；示例数据没有混入真实报告

交付时说明：按「XX 体裁 · XX 行业」生成、采用哪个主题（HTML），以及可以怎么换（更正式 / 更精简 / 换主题 / 转飞书）。
