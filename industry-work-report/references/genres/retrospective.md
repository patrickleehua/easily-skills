# 复盘：项目复盘 / 阶段回顾 / 经验教训

## 定位

回看一个已结束的迭代、阶段、项目或事件，形成可复用的学习，并**改变下一轮的做法**。对事不对人，不是追责，也不是成绩陈列。

**排除**：当前状态与升级需求 → `status-report.md`；仍在止损、取证、恢复的事故 → `incident-report.md`（事故报告末尾可以附复盘的学习层）。

## 硬约束

| 项 | 规则 |
| --- | --- |
| 写作 | 坦诚、无责备、因果克制；不用“加强沟通”“持续关注”代替可验证的改进 |
| 逻辑 | 界定周期 / 事件 → 目标与预期 → 实际结果 → 聚类观察 → 原因（证据充分才叫根因，否则写促成条件 + 验证方式）→ 保留项 → 少量改进实验 → 复查点 |
| 事实 | 观察、解释 / 假设、洞见、行动分层；结论回链事件、指标或交付物；不补造指标、时间线、共识、原因 |
| 失败 | 周报换标题、情绪宣泄、个人归罪、单一根因臆测、行动无 owner / 验证 / 跟踪、不回看上一轮行动效果 |

## 默认框架 GRAI

- **G 目标回顾**：当初目标是什么？成功标准是否清晰可衡量？
- **R 结果评估**：实际发生了什么？与目标对比，亮点和不足各是什么？（用数据）
- **A 原因分析**：差距为什么产生？区分主观 / 客观、事实 / 观点；证据不足时写“促成条件 + 验证方式”。
- **I 规律总结**：学到什么、哪些可复用？产出 KISS（Keep / Improve / Start / Stop）并挑 1–3 个改进实验。

便签、4Ls、Start / Stop / Continue 只是收集手段，成稿要综合成主题和判断。个人成长类复盘以一个真实事件为证据：当时判断 → 反证 / 后果 → 新认识 → 下一次可观察的行为。

改进实验写：动作、负责人、时间、验证条件、跟踪位置；优先改系统、流程、工具，而不是要求人“更小心”。

## HTML 组件配方

| 位置 | 组件 |
| --- | --- |
| 首屏 | `summary` + `highlights`（保持 / 改变 / 下一轮实验） |
| G 目标 | `scorecard`（目标 vs 结果） |
| R 结果 | `timeline`（关键节点，异常节点标 risk / delayed） |
| A 原因 | `waterfall`（偏差由什么构成）/ `fishbone`（多因素）+ `evidence`（事实与推断分开） |
| I 规律 | `grid`（KISS）+ `actions`（改进实验）；排优先级可用 `quadrant` |

示例：`assets/examples/retrospective.json`。
