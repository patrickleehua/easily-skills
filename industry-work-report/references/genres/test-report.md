# 测试报告：测试 / 验收 / 质量 / 上线 / 回归 / UAT 报告

## 定位

报告一轮测试或验收的执行情况和质量结论，读者要据此判断“能不能进入下一阶段（提测 / 上线 / 交付 / 验收签字）”。

**排除**：对照标准做全面合格性审查并出整改要求 → `review-audit.md`；比较技术方案 → `tech-validation.md`。

## 硬约束

| 项 | 规则 |
| --- | --- |
| 写作 | 数据驱动、结论明确（通过 / 不通过 / 有条件通过） |
| 逻辑 | 质量结论 → 测试范围与版本 → 执行情况 → 缺陷情况 → 未覆盖项与风险 → 准出建议 |
| 事实 | 用例数、执行数、通过率、缺陷数都要写统计口径和时间点；未执行、阻塞的用例单列，不算通过 |
| 准出 | 准出标准事先写明（如 P0/P1 缺陷清零、通过率 ≥98%）；逐条对照，不达标项写处置 |
| 失败 | 只报通过率不报覆盖、遗留缺陷不列、未测范围不写、准出标准缺失或事后调整 |

## 结构骨架

1. **质量结论**：是否满足准出；遗留风险一句话。
2. **范围与版本**：被测对象、版本号、环境、测试类型（功能 / 性能 / 兼容 / 安全）、时间。
3. **执行情况**：用例总数、执行、通过、失败、阻塞、未执行。
4. **缺陷情况**：按严重程度和模块分布、趋势、遗留缺陷清单。
5. **未覆盖项与风险**：没测到的场景及原因。
6. **准出对照与建议**：逐条准出标准 → 是否满足 → 处置。

## HTML 组件配方

| 位置 | 组件 |
| --- | --- |
| 首屏 | `summary` + `kpis`（用例数 / 通过率 / 遗留缺陷 / 阻塞）+ `highlights` |
| 执行情况 | `stacked`（通过 / 失败 / 阻塞 / 未执行）或 `donut` |
| 缺陷 | `bar`（按模块）+ `heatmap`（模块 × 严重度或模块 × 日期）+ `line`（新增 / 关闭趋势） |
| 遗留缺陷 | `table`（`level` + `status` 列） |
| 准出 | `checklist`（逐条准出标准） |
| 结论 | `decisions` 或 `callout` |
