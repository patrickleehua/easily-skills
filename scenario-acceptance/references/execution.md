# 按场景执行与收集证据

## 选择执行路径

| 被验收对象 | 优先使用的真实入口 | 证据边界 |
|---|---|---|
| 网页用户流程 | 可用的浏览器控制工具或已有 E2E 脚本 | 实际点击、输入、读取渲染结果；接口直调不能代替 UI 链路 |
| 原生桌面或移动应用 | 对应平台可用的控件、截图、鼠标键盘或设备自动化 | 先探测窗口／设备是否可操作；不能由网页预览推出原生通过 |
| Canvas、游戏或多用户流程 | 真实运行画面与输入工具、所需会话和角色 | DOM 工具不保证能识别画布；单账号不证明多人同步 |
| API、CLI、事件或协议 | 实际接口、命令或消息入口 | 检查契约、输出及相关副作用；按需求保留真实依赖边界 |
| 核心规则 | 已有单元或组件测试、独立计算判据 | 适合边界和组合；不证明部署、界面或跨服务链路 |

文字用例的执行者可以是 AI、人或脚本。使用当前宿主已提供的工具，遵守该工具的操作规范；不承诺所有宿主或系统天然可控制。只有需要确定、重复的动作且现有工具不足时才考虑新增脚本。

## 开始一次验证

记录当前被测版本、必要配置及服务版本；仓库存在未提交改动时说明，不能只用 HEAD 冒充实际代码状态。按现有约定记录 run 标识；普通任务时间戳和版本说明即可，不强制新数据库或收据系统。

在大批或昂贵场景前，用一条代表性短路径核验工具是否可信：

- **目标**：实际页面、窗口、设备或接口属于当前被测版本和环境，定位器命中所需控件。
- **身份与数据**：当前登录者、角色、会话、记录标识和前置状态与场景一致，不能只凭登录成功认定身份正确。
- **动作与结果**：动作到达目标，能读取动作后的新状态，并按独立预期区分结果；必要时用已知状态或现成失败样本核对判别能力，不能仅凭工具无报错判定通过。

探测检查的是执行与观察能力，不要求产品先通过。若已能可靠观察到真实业务失败，照实记录并按影响继续；若工具认错页面、身份、数据或读不到结果，则暂停依赖该能力的批量执行，先修正或交接受阻条件。独立场景可继续。已有仍有效的探测可复用，目标、身份准备或观察方式变化使其失效时再补，不新建探测框架或递归验证工具。

检查数据准备与清理会影响什么，优先隔离测试账号和环境；不假定“测试”授权真实付款、对外发消息或破坏生产数据。也不为确认工具判别能力制造未经授权的业务副作用。

在已有约定内准备场景前置条件。需要重新登录、重置状态、多个角色或独立会话时实际做到；无法建立状态就明确受阻，不伪造输入或结果。

## 操作与判定

执行动作后读取新的界面、输出或相关状态，再决定下一步。关键等待基于可观察条件和合理超时；不要靠固定延迟或反复点击掩盖问题。

按需求检查最终结果。例如“设置保存”可用刷新、重进或权威查询验证；“重复提交不重复扣款”还需观察对应次数与金额。检查方法必须有当前环境的访问依据，不能虚构数据库、日志或监控权限。

优先用可确定的字段、数量、状态和明确提示判定，视觉／体验问题以截图和具体标准辅助。测试预期不从当前实现输出复制；模型主观判断不充当已经落实的程序硬门禁。

截图、trace、命令原始输出或脱敏日志按问题价值选择；复用已有输出，无须给每次点击建文件或重复收集等价材料。保存足够复现和审查的材料，避免秘密进入报告或分发包。未观察到的结果保留未知。

## 结果语义

若宿主已有状态使用等价映射，避免改变原有流程状态：

| 结果 | 判定 |
|---|---|
| 通过 | 本次前置成立，相关动作和检查实际执行，结果满足预期 |
| 失败 | 在有效条件下观察到与已确认预期的差异 |
| 受阻 | 已知必要环境、操作、观察或判据条件缺失，无法完成该验证 |
| 未执行 | 本轮尚未运行，或明确不在本轮执行范围 |

执行中断、超时、重试、跳过及其原因保留在记录中。工具报错或服务不可达先记录事实，再定位归因；有明确超时契约且触发条件有效时，可将违反该契约记录为失败。

执行器的原始错误、场景结果和原因归类分别说明，不新增状态机。例如定位器报错可保留脚本运行失败记录；若尚未观察业务结果，场景按宿主等价语义记受阻或未执行，不能算产品失败。之后查明原因或复跑通过，追加依据和新结果，不覆盖原记录。

| 用例 | 版本／环境 | 结果 | 实际观察 | 证据／后续 |
|---|---|---|---|---|
| AC-01 | 构建 B42／测试环境 | 失败 | 重新登录后恢复原昵称 | BUG-01，截图与执行记录 |
| AC-02 | 构建 B42／测试环境 | 受阻 | 尚无可登录的隔离账号 | 准备账号后从前置重跑 |

## 差异分析和修复

问题至少说明对应场景、复现数据／步骤、预期、实际、影响、版本环境和证据。无法稳定复现时保留出现条件和频率，不因下一次通过就抹去原始失败。

先核对前置、独立预期、实际观察与工具能力，再选择纠正路径；原因未明时保留待判，不强行归为产品或环境问题。

| 原因 | 纠正路径 | 复跑范围 |
|---|---|---|
| 产品失败 | 有效条件下观察到违反契约的结果；获准后修产品根因 | 最终相关版本上的原失败场景及受影响旧行为 |
| 脚本或用例错误 | 按现有需求、协议或已确认规则纠正错误预期、夹具、定位器、等待或结果读取 | 先核修正后的执行／判定能力，再跑原受影响场景；共享夹具或工具改动时覆盖实际受影响场景 |
| 环境受阻 | 核实缺失的服务、身份、数据、设备或权限，恢复有效前置；产品自身违反可用性契约不能仅归环境 | 恢复后从有效前置执行受阻场景及因此失效的检查 |
| 需求歧义或真实规则变更 | 把具体分歧交原决策渠道，确认后同步相关用例与执行资产 | 重新判定受影响场景，保留旧规则下的历史结果 |

修复生产代码、脚本或用例均遵守原写入授权；测试只读任务输出问题即可。纠正与现有契约不符的测试预期不是需求变更，无需虚构变更单；须保留原错误、权威依据、修改及复跑结果，不能照抄产品当前输出改预期。产品结果错误应提交缺陷，修好脚本不等于修好产品。跳过项始终披露，不改名为通过。

复跑范围由改动影响和证据是否失效决定，不默认整套重跑、重写场景或重建夹具与工具；项目明确要求全量回归时仍执行。需要长期保护且已有工具合适时补充复现测试；不强制每条业务用例或每个视觉调整生成永久脚本。临时诊断可留下本次证据而不进入正式测试集。

## 能力不足与停止

对已知障碍仅做授权内、低成本且可回退的恢复。恢复无新线索时停止，继续能执行的用例；保留具体缺失项、尝试记录及复跑入口。替代证据标明覆盖层次，不能将静态审查、mock 或历史通过换算成当前真实验收通过。

本次必做检查完成、最终版本相关证据充分且必要缺口已处理后停止；不因“再多测一些更保险”或“再造工具证明工具有效”无限扩建。只在具体证据失效、新失败／相关风险暴露缺口或原验收另有要求时重开受影响范围。修复循环不收敛时按现有时间／轮次约定交接；无约定且已无合理新假设时，报告事实和下一步选项，不自动扩大改动。
