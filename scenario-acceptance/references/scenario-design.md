# 编写和评审文字用例

## 从真实业务结果拆场景

先找到需求中的行为、参与者、状态变化及必须保留的旧行为，再选择可区分成功与错误的例子。把“做了什么”和“如何知道做对了”同时写出来。

对与本次需求相关的风险按需考虑：

- 主流程和取消、返回、重试、重复提交；
- 输入边界、空数据、无效输入和关键组合；
- 不同权限、前置状态、状态转换及禁止操作；
- 跨页面、服务、会话或设备的持久化和同步；
- 依赖失败、超时后的用户反馈及最终副作用；
- 相邻旧流程、接口兼容和历史缺陷。

这些是选例提示，不是每项需求都必须填满的检查清单。按风险挑选；等价输入用参数表表达，不把不同权限或失效机制合并为一个“异常测试”。

## 足够执行的最小格式

可使用项目现有表格；无现成格式时参考：

| 字段 | 内容 |
|---|---|
| 标识／来源 | 稳定用例编号与需求条款、工单或确认记录 |
| 场景 | 用户希望完成的事，或必须被阻止的行为 |
| 前置／数据 | 身份、状态、输入、必要依赖；相关数值明确 |
| 操作／事件 | 可执行步骤或触发事件 |
| 预期 | 能观察并判定的结果，必要时列禁止结果 |

执行入口、风险优先级、清理方法、自动化候选等字段按实际需要添加。运行状态、证据和缺陷链接属于执行记录，避免修改一次状态就改变业务预期。

可以用 Given／When／Then 的语义组织中文，不要求引入 Gherkin 或 Cucumber。

## 示例：昵称持久化

假设需求 R-01 已明确昵称允许 1～20 个 Unicode 码点。这里的计数规则仅为示例，真实项目必须从其需求取得。

**AC-01：有效昵称保存并在重新登录后保留**

- 来源：R-01。
- 前置：隔离测试账号已登录，原昵称为“小明”；测试服务可用。
- 操作：打开个人资料，将昵称改为“小华”，保存，刷新，再退出并重新登录。
- 预期：昵称为“小华”；需求指定的个人资料与用户主页一致；重进后仍为“小华”。

**AC-02：超过上限不改变原昵称**

- 来源：R-01；输入为 21 个已知码点组成的字符串。
- 前置：昵称为“小明”。
- 操作：尝试保存超长昵称，重新进入个人资料。
- 预期：操作被拒绝并给出可理解的原因；昵称仍为“小明”。

相邻检查可包含恰好 20 个码点、空输入等；已有有效覆盖时复用。若“空格是否去除”“emoji 如何计数”“同步到哪些页面”未定义，列出具体分歧与建议，不自行决定后写成正式断言。

## 控制详细程度

业务预期要精确，操作细节仅写到可执行。一个场景聚焦一个可说明的业务行为；长流程可保留完整用户旅程，分开标识关键检查点，避免失败后无法定位。

不要在业务场景中固化 CSS 选择器、像素坐标、内部函数名或盲等时长。这些放入执行层；界面入口名称可以保留，必要版本差异另记。不要通过列出所有实现分支反推预期，避免把实现错误写进用例。

## 评审判断

检查来源是否权威、前置是否能准备、预期是否能独立判定、是否覆盖关键边界和旧行为影响。重点审查高风险业务的预期；无需给每条明确场景增加人工审批。业务规则变更先经项目原有渠道确认，再同步受影响用例及执行资产，不回写历史运行结果。
