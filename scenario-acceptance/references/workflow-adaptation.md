# 接入现有研发流程

## 先找职责，不根据框架名称规定流程

阅读目标仓库的 AGENTS.md、当前需求与验收文件、SOP／专家角色、实际命令和生成／安装入口。确认谁定义业务、谁实现、谁执行验证、谁接受风险及最终发布；沿用已有权限、必做检查、专项方法、输出状态和人工出口。

按实际工作分配职责，不要求固定人员、职位名称或 Agent 数量：

| 工作职责 | 应做的事 | 需要守住的边界 |
|---|---|---|
| 业务／需求负责人 | 确认目标、业务规则、关键预期和范围变更；接受产品风险 | 不以实现现状反推应有业务行为 |
| 实现者 | 阅读相关场景、实现功能、自测、提供可运行版本和验证证据；获准后修复问题 | 不能单为消除失败擅自降低预期 |
| 测试执行者 | 准备用例和环境，实际操作，补充相关探索，报告差异和证据 | 测试权限不自动扩大为修改产品或发布权限 |
| 评审者 | 对照需求检查场景遗漏、预期依据、实现影响及证据充分性 | 静态评审不冒充运行通过；独立角色也可能共享同一错误假设 |
| 环境／发布负责人 | 准备依赖、身份、隔离数据及设备，按现有程序发布和恢复 | 测试通过不自动触发生产发布 |

一个人或 Agent 可以承担多个职责；重要验收按需要增加独立复核，业务裁决和发布授权仍归原有负责人。只有明确要求真实独立复核时，才需要不同审查者，不能以同一角色自述冒充独立审查。

将本技能插入已有工作节点：

| 已有节点 | 加入的能力 |
|---|---|
| 需求澄清／验收标准 | 将业务结果写为可判定场景，标明来源、待决规则及兼容要求 |
| 设计／任务拆解 | 让对应场景对实现者可见，明确如何准备、执行及观察 |
| 实施／自测 | 围绕场景实现，按风险选必要的代码测试和实际验证 |
| 测试／评审 | 先核工具能正确识别目标、身份、数据和结果，再按已确认预期实测；记录差异及适量证据 |
| 修复／交付 | 区分产品失败、脚本错误与环境受阻，分别修复或恢复；原受影响场景复测和影响回归，保留未验事项与原验收出口 |

不强制每个项目新增独立阶段、固定目录、固定数量文档或新状态机。已存在的验收场景直接复用；与权威需求冲突时解释分歧，不维护两份互相矛盾的规格。

## 不同载体的映射示例

以下是语义映射，不是保证各版本命令或目录一致的安装指南。

| 载体 | 用例如何承载 | 实施与验收如何接 |
|---|---|---|
| OpenSpec | 当前变更的 requirements／scenarios，或既有测试计划；避免重复业务预期 | 在实际 tasks 与 apply／verify 约定中关联场景、执行方式和证据；读取项目当前 schema |
| Spec Kit | 当前需求的用户故事／验收场景，及项目已有测试说明 | 对应 plan／tasks 安排验证；测试先行仅在项目选用或原规则要求时落实，并确认生成任务实际包含 |
| 其他 SDD、PRD、工单或普通迭代 | 现有验收条款或关联的 Markdown／表格 | 沿原任务推进，在交付前逐项核对并留运行记录 |
| 仅要求测试或只读评审 | 需求与现有用例，必要时提出缺口 | 只执行获准验证和报告；不顺带开发、改验收或发布 |

采用某个框架不证明其规则已加载或执行。接入时检查实际源文件、生成物及宿主可用能力；源模板更新不等于运行中的实例更新。不要凭本页示例猜 slash 命令。

## 文字、TDD 与自动化的组合

文字场景负责业务含义；执行路径可以是 AI 操作、人测、现有测试或新脚本。文字用例先行不等于 TDD，也不要求每条业务场景自动化。项目已要求 TDD 时保留先失败再通过的实际运行，不能用文字提前编写替代红绿证据。没有 TDD 要求时，本技能不强制增加它。

可先由 AI 依据文字场景探索并验收，再把稳定、高频的回归部分保存脚本。核心规则组合可以在较低层验证；端到端场景保护真实接缝和用户流程，不把每个输入组合复制到所有层。

重要验收可让独立角色从需求重新检查遗漏和预期；复用现有审查职责，不默认创建第二个 Agent 或另一套团队。共享同一错误预期仍可能漏检；角色分离不等于独立业务事实。

## 与其他能力的边界

本技能负责“业务场景怎么表达、怎么实际验证、如何关联问题和证据”。已有的代码评审、投入取舍、性能、安全或其他专项方法继续负责各自问题，不要求安装另一项技能。原有执行宿主管理派发、权限、超时、恢复和状态。

## 技术栈与扩展

本技能以 Markdown＋YAML 分发，无执行脚本和包依赖。实际测试依赖项目自己的运行环境与宿主工具，跨系统能否操作和观测需分别确认；文档可移植不代表 UI 工具已在 Windows／Linux／macOS 全部实测。

将来有明确、重复、可确定的动作才新增工具：共享复杂核心可用 TypeScript 并发布 JavaScript，低依赖独立工具可用 .mjs，数据／文档／模型工具可用隔离的 Python＋uv，Shell／PowerShell 仅做平台适配。复用成熟工具，不为文字验收重建 Harness。

新增工具后再定义版本化输入输出、错误、超时、依赖锁定、显式副作用和恢复行为，分别验证相应平台及真实宿主。程序可强制执行明确检查与权限；不能把模型自报成功当作确定性门禁。

## 可直接嵌入 SOP 的片段

> 使用文字验收场景连接需求、开发与验证。场景关联业务依据，说明前置、操作和可观察预期，开发前对实现者可见；文字先行不等于 TDD，也不要求逐条自动化。大批执行前先用短路径核验工具能正确识别目标、身份、数据和当前结果，再在真实入口验收，记录版本、结果和适量证据。产品失败、脚本错误、环境受阻分别归因：获准后修产品、按现有契约纠正错误测试、恢复环境，复跑原受影响场景及影响回归；纠正错误测试不要求虚构需求变更，真实规则变化仍交原渠道。失败、受阻与未执行不得记为通过。分开决定必要验证、永久测试、临时诊断与交付证据，复用有效证据，一次性检查不必永久化；必做检查完成、证据充分且必要缺口已处理即收口，不默认全量重建或递归验证工具。保留既有专项方法、角色权限、状态及人工验收出口。

## 试用判断

先静态检查接入位置，再在获准真实任务中观察：能否识别关键差异、是否擅自改预期、未验是否如实披露、环境缺口能否恢复、重复维护是否值得。可选代表场景包括低风险展示、少行高风险规则、跨服务保存、只读验收、设备缺失和已有强制 TDD。案例推演和格式校验只能说明指令设计与结构，不能宣称已证明产品缺陷检出率或跨宿主兼容性。
